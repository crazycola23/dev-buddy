# 跨层垂直切片

仅在任务跨越有意义的系统边界，或现有契约与调用链不清楚时读取本文件。

## 从行为出发

先写一条用户可观察的验收结果，再只追踪它实际经过的节点：

```text
用户动作
  → 页面或调用入口
  → 前端状态
  → 请求与契约
  → 后端边界
  → 业务规则与事务
  → 数据库或外部服务
  → 响应与错误映射
  → 页面或调用方反馈
```

并非每个任务都有全部节点。省略没有经过的层，不为追求图完整而读取无关代码。

## 只建立受影响地图

按需确认：

- 前端入口、状态、请求客户端、共享类型和相关测试；
- 后端入口、业务规则、持久化边界、配置和相关测试；
- 数据模型、约束、迁移、索引与事务边界；
- API、事件或 schema 的字段、错误和版本语义；
- 认证、外部服务、运行配置及必要的诊断信息。

从当前入口沿直接调用关系前进。不要枚举整个 monorepo，也不要因为功能跨层就重新组织模块。

## 停止规则

当以下事实都有证据时，停止扩大阅读范围并开始实现：

1. 用户行为对应的入口与返回位置已确定；
2. 受影响边界的输入、输出和所有者已确定；
3. 业务规则、数据副作用和主要失败表现已确定；
4. 项目用于处理同类问题的约定已确定；
5. 可以指出用什么验证验收结果。

遇到缺口时只补读能回答该缺口的文件。

## 对齐各层

1. 固定 API 或事件契约及错误语义；
2. 实现可信边界上的校验、权限、业务规则和数据行为；
3. 实现调用方请求、状态和用户反馈；
4. 同步类型、调用方、迁移和测试；
5. 验证成功路径及与本次改动相关的失败路径。

实现顺序可以适配项目，但不要让边界两侧各自猜测契约。

## 检查跨层一致性

- 字段名、可空性、枚举、时间、金额和分页语义一致；
- HTTP 状态、业务错误和调用方反馈对应；
- 授权在可信边界执行，而不只隐藏界面元素；
- 数据约束支持业务不变量，迁移兼容已有数据；
- 加载、空数据、部分失败、重复提交和网络中断有合理表现；
- 缓存、重试、并发和异步行为不会产生陈旧数据或重复副作用；
- 日志足以定位跨层失败且不泄露敏感信息。

只检查与当前切片和风险有关的项目。

## 处理框架事实

从锁文件、BOM、构建配置和实际 import 确认版本。对不确定或版本敏感的 API，只采用对应版本的官方文档、规范、源码或发布说明，并区分项目事实、官方事实和仍需验证的推断。
