# 全栈链路工作流

在任务跨越前端、后端、数据层或外部集成，或者现有链路不清楚时读取本文件。

## 建立项目地图

只读取与任务有关的入口和清单，记录证据而不是猜测：

- 前端：包清单、路由、页面入口、组件、状态管理、请求客户端、类型和测试；
- 后端：构建文件、启动入口、控制器或处理器、服务、领域逻辑、仓储、配置和测试；
- 数据：模型、迁移、约束、索引、种子数据和事务边界；
- 契约：OpenAPI、GraphQL schema、共享类型、DTO、序列化、错误格式和版本策略；
- 运行：环境变量、容器、代理、认证、日志、监控和 CI 命令。

尊重 monorepo、multi-module 或多仓库已有边界。不要因为一个功能跨层就重新组织整个项目。

## 绘制一条真实链路

使用最小可读表示：

```text
用户动作
  → 页面/组件
  → 本地或共享状态
  → 请求与 API 契约
  → 后端入口与边界校验
  → 业务规则与事务
  → 数据库或外部服务
  → 响应与错误映射
  → 状态更新与页面反馈
```

只保留本次功能经过的节点。对每个边界确认：输入、输出、所有者、失败表现和验证位置。

## 定义垂直切片

先写用户可观察的验收条件，再对齐各层：

1. 确定 API 或事件契约以及错误语义；
2. 实现业务规则、权限和数据行为；
3. 实现前端请求、状态和交互反馈；
4. 同步类型、调用方、迁移和测试；
5. 用至少一条成功路径和相关失败路径验证整条链路。

实现顺序可以适配项目，但不要让前后端各自猜测契约。

## 检查跨层一致性

- 字段名、可空性、枚举、时间、金额和分页语义是否一致；
- HTTP 状态、业务错误和前端提示是否对应；
- 认证与授权是否在可信边界执行，而不只是在 UI 隐藏按钮；
- 数据库约束是否支持业务不变量，迁移是否兼容现有数据；
- 加载、空数据、部分失败、重复提交和网络中断是否有合理表现；
- 缓存、重试、并发或异步行为是否会造成陈旧数据或重复副作用；
- 日志和追踪是否足以定位跨层失败，同时不泄露敏感信息。

## 处理框架事实

先从锁文件、BOM、构建配置和实际 import 确认版本。对新框架、版本迁移或记忆不确定的 API，只采用对应版本的官方文档、规范、源码或发布说明。区分：

- 项目中已验证的事实；
- 官方资料支持的事实；
- 仍需运行或实验验证的推断。

不要把“通常如此”写成当前项目的事实。
